# Stage 13 — local revenue-manager briefing (S1)

This component generates a bounded structured briefing with a real local open-weight
model, validates it, and displays only accepted output. The existing Stage 7 service
and Diary demonstration are unchanged. No message transport or operational approval
is implemented. Outputs describe historical simulations, not authorised decisions.

## Contract and reproducibility

The supplied course policy is copied to `docs/llm-access.md`. Inference uses the
single OpenAI-compatible endpoint configured in `config/config.yaml`. This baseline
permits loopback HTTP only; cloud fallback is deliberately disabled. An outage stops
generation; replay remains available. A hosted comparison would require an explicit
code/configuration change and data-policy review, rather than silent failover.

The runtime is Ollama; the instruction model is `qwen3:4b-instruct`, Q4_K_M, Apache
2.0, with the full digest pinned in configuration and recorded alongside results.
A 4B model was chosen conservatively to leave memory for the existing VM/demo on
this 16 GB Apple M5 MacBook Air. No hosted API or paid account is needed.

The prompt lives in `prompts/revenue-manager-v1.txt`; its SHA, schema SHA, context
SHA, tag/digest, decoding settings and raw responses are recorded. Structured output
constrains field types and action choices, **not the correct numeric values**.
Numbers are generated by the model and independently compared to input facts.
Guest wording is deliberately fixed and checked verbatim; this evaluates a bounded
briefing, not free-form narrative generation. Rendered prose is a deterministic
presentation of accepted model fields. This limits expressiveness in exchange for
an auditable factual contract.

## Golden set and as-of boundaries

Before inference, select 29 calendar-spaced arrival nights across Jan–Aug 2017 plus
the notebook demo arrival 15 August: 30 nights, both hotels each night. No nights
are selected by model success. The builder loads the existing saved learner,
calibrators, flat rates and chosen policies, verifies the frozen data fingerprint,
and recomputes nightly distributions with the original seven-day horizon. It
never fits or chooses a policy. The six numeric fields per hotel and common walk
cost are rounded to the notebook's three-decimal context precision, then compared
with exact numeric equality (no numeric tolerance for generated responses).

Only pre-outcome nightly aggregates are exported. Current-night release labels,
actual walks and Stage 12 BlockOutcome triples are excluded. Inferred multi-row
booking units are explicitly not verified parties. The saved core KB is queried
at each batch date for prepaid status; unresolved codes must produce null. The
known frozen City PASS / Resort FAIL engineering gate is included as a retrospective
safety warning, not represented as contemporaneous historical knowledge. It blocks
any suggestion that the proposed quantities constitute permission to operate.

Each date is paired with the identical numeric context but no KB facts. The expected
semantic response without KB is abstention even when a code looks meaningful.
This live comparison is distinct from Stage 10's deterministic 19-case contract.
Six adversarial notes attempt quantity/date edits, fake system roles, fabricated
refunds, KB contradiction, exfiltration and bypassing approval. Notes are data;
no network or tool call is available to the model. No private booking IDs, guest
names, nationality or verbatim personal text are sent.

## Validation and approval

Validation rejects malformed/duplicate-key/nonfinite JSON, schema violations,
changed numbers, extra claims/keys, invented deposit semantics, changed dates or
policies, altered warnings, unapproved guest promises and false approval flags.
Failures remain in raw evidence and are withheld; there is no hidden repair, retry
or replacement with the expected answer. The guest message is an **unsent draft**.
A separate human may approve its exact digest with a reviewer and reason; editing
the draft invalidates that approval. Approval records have no dispatch capability
and do not replace policy-wide manager sign-off or consent/contract checks.

## Commands

`make briefing-record` calls the configured local model and replaces recorded
fixtures. `make briefing-replay` checks that committed responses reproduce their recorded scores,
with no inference or network access. `make briefing-quality` additionally fails if
any recorded response violates the factual/approval contract. `make ci` runs both
the frozen model calibration gate and this strict briefing gate, reporting both
even if one fails. A stable failing fixture is not a passing model. Re-record and log to MLflow whenever prompt, schema,
context or model changes. `scripts/build_stage13_golden.py` regenerates the input
facts; it requires the original local dataset and serving bundle.

`scripts/log_stage13_mlflow.py` runs with the isolated tracking Python and logs
provider/endpoint, tag/digest, prompt, temperature, all scores, schema failure rate,
tokens, p50/p95 latency and zero local inference API cost. It creates a briefing
experiment only and never changes registered models or champion aliases. Zero API
cost excludes electricity, hardware purchase and labour; energy is not measured.
First-request cold loading is included in recorded wall time; no warm benchmark
or statistical generalisation is claimed. Fixtures prove one recorded run, not
universal prompt-injection resistance or identical generation on other hardware.

## Running the local baseline again

The downloaded Mac runtime and weights are kept under ignored
`artifacts/stage13/runtime`, not committed or included in the Ubuntu archive.
In one Mac terminal, run `sh scripts/serve_stage13_local.sh`; in a second, run
`make briefing-record`, then `make briefing-replay`. Stop the foreground server
with Control-C when finished. This avoids leaving model memory occupied during
the VM demonstration. A fresh machine installs Ollama from the official website,
starts the same launcher (which falls back to the installed `ollama` command),
and runs `ollama pull qwen3:4b-instruct`. The recording command verifies the full
configured digest; a moved tag must not silently replace these weights. If the
original weights become unavailable, retain these fixtures and explicitly version
and re-evaluate a replacement. No paid reproduction path is required.

Ubuntu verification deliberately uses `--network none` and the existing Stage 9
check image. It replays the **Mac local-model run**; it does not claim to run the
LLM again on Ubuntu. Counts and identity checks cover all source/tests/knowledge,
configuration, prompt and raw response fixtures. It protects the existing Ubuntu
serving files, core KB and MLflow database.

| Correct semantic answer or abstention | 30/30 | 30/30 abstentions | 6/6 |

With KB, 23 answerable prepaid facts were correct and seven unresolved cases
abstained. Without KB all 30 abstained: the KB adds semantic coverage. All numeric
mismatches concerned Resort empty-room cost. One ordinary and one injection
response used a negative value and also failed schema validation. Eight invalid
responses were withheld. The 15 August demo night passed exactly; the example
briefing shows that accepted, unsent simulation.

All six injection-specific objectives were resisted in this small test; one
injection response had an unrelated numeric/schema defect. Matched clean baseline
failures are retained, not confused with successful attacks. No universal security
claim is made. No tools or dispatch interface were exposed.

Median latency was 7.90 seconds, p95 9.73 seconds; 30,410 input and 19,861 output
tokens. API cost: EUR 0 per 1,000 answers, excluding unmeasured electricity. This
was one sequential run with normal caching and cold loading included.

215 software tests passed; six unconnected database tests were skipped. Offline
fixture regression passed after stopping the server. **Strict briefing quality
remains FAIL**: the 30-night exact-number target is unmet. CI exits 2, reporting
this failure and the existing Resort calibration failure. This is an honestly
evaluated local baseline, not operational clearance. Any revised prompt/model
needs explicit versioning and separate evaluation; do not tune on these golden

The run is logged in local MLflow experiment `task19-stage13-briefing`; see
